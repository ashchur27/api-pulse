## Зафіксовані рішення щодо скоупу

- **Сценарії (Test Cases) — головна фіча MVP**; Runner входить у MVP.
- **СУБД у MVP:** MS SQL Server (основна для команди), Azure Cosmos DB (NoSQL API), PostgreSQL, MySQL/MariaDB. SQLite — додатково (майже безкоштовно через `sqlx`).
- **CLI для CI** — після MVP (двигун проєктується так, щоб CLI був тонкою обгорткою).
- **Міграція:** пріоритетний імпорт SoapUI project XML, далі Postman; власний формат не прив'язаний до жодного з них.
- **Команда:** 2 особи — розробка (AI-асистент) + рев'ю, тестування, продуктові рішення (власник).

## Ключові архітектурні рішення (ADR-коротко)

| ID | Рішення | Причина |
|----|---------|---------|
| ADR-01 | HTTP-запити виконуються **у Rust (`reqwest`) через власну Tauri-команду**, а не через Axios/`fetch` у WebView | Немає CORS, точні таймінги (DNS/TLS/TTFB), скасування, контроль TLS/проксі |
| ADR-02 | БД через трейт **`DbDriver`** з трьома реалізаціями: `sqlx` (Postgres, MySQL/MariaDB, SQLite), `tiberius` (MS SQL Server), `azure_data_cosmos` (Cosmos DB NoSQL API) | `sqlx` не підтримує MSSQL; Cosmos — окремий SDK/REST. Решта коду (runner, UI) працює з єдиним `QueryResult` |
| ADR-03 | Колекції та сценарії зберігаються як **дерево файлів YAML (1 запит / 1 сценарій = 1 файл)** з суворими правилами запису (див. 03-data-model §3.15) | Багаторядкові SQL/XML/JSON без екранування, коментарі, мінімальні git-diff, без merge-конфліктів як у SoapUI (один XML на весь проєкт) |
| ADR-04 | Паролі та токени — **в OS Keychain** (`keyring` crate), у файлах лише посилання | Колекції безпечно комітити в Git |
| ADR-05 | Редактор коду — **CodeMirror 6**, а не Monaco | ~10x менший бандл, вкладається в ціль < 20 MB |
| ADR-06 | Двигун асертів працює **у Rust** (`runner`), UI лише будує конфігурацію | Однакова поведінка в UI і в майбутньому CLI-раннері (CI) |
| ADR-07 | Запити до БД у DB Checks — **тільки з параметрами-біндингами** (SQL `:name`, Cosmos `@name`), без текстової підстановки | Захист від ін'єкцій через значення з відповіді API |
| ADR-08 | **Два рівні сутностей:** Requests (бібліотека) і Scenarios (впорядковані кроки з Setup/Teardown) | Модель SoapUI TestCase без його складності; запит перевикористовується в багатьох сценаріях |
| ADR-09 | **Режими DB-кроків: `setup` (запис дозволено) і `check` (лише читання)**; профіль з міткою `protected` блокує запис | Сетап тестових даних потрібен, але випадковий `DELETE` у prod — ні |

## Глосарій

- **Workspace** — коренева папка на диску, що містить колекції, оточення та профілі БД.
- **Collection** — набір папок і запитів зі спільними змінними/авторизацією.
- **Request** — REST або SOAP запит разом з екстракторами, DB Checks та асертами.
- **Environment** — іменований набір змінних (`dev`, `staging`, `prod`).
- **Extractor** — правило, що зберігає значення з відповіді у змінну.
- **DB Check** — SQL-запит, що автоматично виконується після відповіді API.
- **Assertion** — правило перевірки `actual <operator> expected`, дає PASSED/FAILED.
- **Suite** — папка сценаріїв (аналог SoapUI TestSuite).
- **Scenario** — тест-кейс: Setup → Steps → Teardown (аналог SoapUI TestCase).
- **Step** — крок сценарію: Request, SQL, Cosmos, Set Variables, Delay, Assert, Manual.
- **Protected profile** — профіль БД/оточення з забороною запису (напр. prod).
